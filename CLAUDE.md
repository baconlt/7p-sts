# 7 Presidents STS — Lifeguard Scheduling System

## Architecture
- Google Apps Script web app (Code.gs + index.html + Board.html)
- Google Sheets backend
- PWA wrapper hosted on GitHub Pages (baconlt.github.io/7p-sts)

## Apps Script files (apps-script/)
- `Code.gs` — all server-side logic, auth, CRUD
- `index.html` — entire frontend SPA (HTML + CSS + JS in one file)
- `Board.html` — public no-auth beach assignments display page (served at `?board=1`)

## ⚠️ Deployment — no clasp, manual upload required
Changes are NOT live until manually uploaded. After any edit:
1. Open the Apps Script editor
2. Paste updated file(s) into the corresponding tab
3. Save (Cmd+S)
4. Deploy → Manage Deployments → edit the existing deployment → Deploy
- If you added/changed triggers in Code.gs, also run `installTriggers()` once from the editor
- Board.html is a separate file/tab in the editor — create it if it doesn't exist yet

Clipboard shortcut: `! cat apps-script/<file> | pbcopy`

## PWA Wrapper (pwa/)
- Thin iframe wrapper for PWA install + session persistence
- Deploy: push to GitHub repo baconlt/7p-sts (GitHub Pages)
- Bump CACHE version in sw.js on each deploy

## Auth
- Password-only (no Google OAuth)
- Sessions stored in Sessions sheet (90-day expiry)
- PWA wrapper stores token in localStorage, passes to iframe via postMessage
- `Board.html` is intentionally public — no auth check in `getBoardData()`

## Key conventions
- Admin server calls use `arun()` (prepends session token as first arg)
- Guard server calls use `runG()` (prepends session token as first arg)
- Unauthenticated server calls use `run()` (no token)
- All dates stored as YYYY-MM-DD strings
- Work week is Saturday–Friday
- Pay periods follow county schedule
- After editing a shift, re-render the active panel: `if(PANEL==='schedule') renderSchedGrid(); else if(PANEL==='full-schedule-admin') R['full-schedule-admin']();`

## Guard panels
- `dashboard` — guard home; shifts override day-off availability entries in the list
- `my-avail`, `my-schedule`, `full-schedule` (read-only grid)
  - **Availability options come from the schedule** (`availOptionsFor`): base statuses, then one option per **scheduled SPEC shift** that day (`specialOffersFor` — deduped by hours+notes; label = `Shifts.notes` or post name + hours; picking one pre-fills the `S_SPEC` entry's `custom_start`/`custom_end`/`notes`, so the guard never retypes the admin's times), then one per template flagged `offer_in_availability` (`S_T_<code>`). All the SPEC options write the **single** `S_SPEC` entry — `offer` (index, or `-1` for free-form "Other special hours") picks the hours, so choosing another swaps rather than stacks. Selection is matched on hours, not status (`_isSpecialPick`/`_availOptSelected`). Handlers: `pickSpecialOffer` (desktop) / `mobPickSpecialOffer` (mobile; free-form still opens `openSpecialTimeSheet`). Chips name the chosen special via `_avChipText`. ⚠️ A special only appears for guards if it's **unassigned** or its week is **published** (`filterPublishedShifts_`).
  - `my-avail` shows **one Sat–Fri work week at a time** (not the whole pay period), defaulting to **next week**. Navigate with the ‹ › week bar or by swiping (`availWeekNav`/`_attachAvailSwipe`, zone `#av-week-swipe`). State: `availViewWeekStart` (Saturday YMD) + `availViewPeriodId` kept in sync by `ensureAvailWeek()`; navigable weeks come from `availWeekList()` (current + future periods, each week clamped to its owning period so a week's days always belong to one period — preserves the per-period avail/shift data model). Crossing into another period with unsaved changes prompts to discard.
- Polls are surfaced as a **dashboard card** (`pollsCardHtml()`), not a nav panel (`polls` exists in `TITLES` only for completeness). See **## Polls**.

- `CacheHunt` (guard_id, last_ping_date, pings, best_ft, found_at) is auto-created via `ensureCacheHuntSheet_()`. - `Checklists` (id, title, icon, category, steps, sort, active, updated_by, updated_at) is auto-created via `ensureChecklistsSheet_()`. **Admin-authored scenario reference procedures** guards consult situationally (Missing Child, Spinal, Opening/Closing, …). `steps` is newline-separated (one step/line); `active` (`'true'`/`''`) gates guard visibility; `sort` orders within a `category`. See **## Checklists** below.
- `Elections` / `VoteBallots` / `VoteReceipts` are auto-created via `ensureVotingSheets_()` — the **secret-ballot award voting** trio. `VoteBallots` (id, election_id, choice_ids) holds the anonymous choices (random id, **no voter/timestamp**); `VoteReceipts` (election_id, guard_id, voted_at) records **that** a guard voted (**no choices**); the two share no linking key. `Elections` (id, award LOTY/ROTY, round prelim/final, status draft/open/closed, opens_at, closes_at, num_choices, candidate_ids JSON, voter_snapshot JSON, test, prelim_id, created_by, created_at). See **## Award Voting** below.
- `Polls` / `PollResponses` are auto-created via `ensurePollsSheets_()` — the **named (non-anonymous) ranked-choice group poll** pair, completely separate from the voting trio. `Polls` (id, title, question, options JSON `[{id,label}]`, rank_count, results_vis `admin`|`after`|`live`, status draft/open/closed, opens_at, closes_at, audience_snapshot JSON, created_by, created_at). `PollResponses` (id, poll_id, guard_id, ranking JSON, vetoes JSON, submitted_at) — **one row per guard per poll, upserted** (editable until close); `guard_id` is stored (NOT anonymous). See **## Polls** below.

## Award Voting (secret ballot — Lifeguard / Rookie of the Year)
- **Anonymous voting with turnout tracking.** The two facts live in two sheets with **no shared key**: `VoteBallots` = the choices (random id, no voter id, no timestamp) and `VoteReceipts` = that a voter voted (guard_id + time, no choices). The app never joins them, so no admin view links a vote to a voter. ⚠️ This is **app-layer anonymity only** — the spreadsheet owner could in principle correlate raw rows; ballots omit timestamps to blunt that. Accepted threat model.
- **Awards**: `LOTY` (🏆 Lifeguard of the Year), `ROTY` (🌟 Rookie of the Year) — see `AWARD_META_`. **Rounds per award**: `prelim` (pick exactly **2**) → `final` (pick exactly **1**). `num_choices` derives from round. ⚠️ The round value stays `prelim` in data, but **all UI displays it as "Primary"** (not "Preliminary") — keep that wording in any new copy.
- **Candidate pools** (auto, `votingCandidatePool_`): prelim LOTY = all active non-cadets; prelim ROTY = active guards with **rank `Rookie`**. Final round = the admin-selected finalists (2, or more on a tie) via `clientLaunchFinalRound`.
- **Voters** = active non-cadets (`votingEligibleVoters_`). **Cadets never vote** and never see a card. The eligible set is **snapshotted into `voter_snapshot` at open** so later roster churn doesn't move the turnout denominator. Admin/Supe vote like anyone else.
- **Lifecycle** (`electionState_`): `draft` → `open` (bounded by opens_at/closes_at; **auto-opens/auto-closes** on the window) → `closed`; `reopen` clears/extends the close time. Only **one non-test election per award may be `open`** at once (`votingOpenConflict_`). One vote is final — no changing a cast ballot. **`clientLaunchFinalRound` auto-closes the primary** before opening the final (so the primary card drops for guards and the one-open check clears); a primary that has spawned a final is flagged `finalLaunched` (admin hides its Launch/Reopen buttons).
- **Server** (`Code.gs`, after Cache Hunt): guard — `clientVotingCards` (live cards + `hasVoted`), `clientVotingBallot` (candidate list), `clientCastBallot` (validates eligibility/snapshot/choice-count/pool, writes ballot+receipt under a `LockService` lock). Admin (`requireAdmin`) — `clientVotingAdmin` (elections + **aggregate** turnout/tally via `votingAdminView_` — counts only, never identities), `clientCreateElection`, `clientSetElectionStatus` (open/close/reopen), `clientLaunchFinalRound`, `clientResetElection` (test-only wipe), `clientDeleteElection` (test, or real w/ zero votes), `clientNudgeNonVoters` (Slack-DMs the un-voted set, **returns counts only**). Helpers: `votingParseIds_`, `votingTally_`, `votingInSnapshot_`, `votingHasVoted_`, `votingCandidateList_`, `votingDeleteRowsWhere_`, `votingPrettyWhen_`.
- **Client — guard** (`index.html`): `VOTING` global via `loadVoting()` (guard init + GV/impersonation, mirrors `loadCacheHunt`); `votingCardsHtml()` renders up to two dashboard cards placed **directly below `announcementsCardHtml()`** (first content card if no announcements) in both dashes. Each card shows a PRIMARY/FINAL chip + closing time, and states: votable / "✅ Your {Primary|Final} ballot has been cast" / **"officially closed"** (the card **persists after close**, non-clickable — `clientVotingCards` surfaces the one current round per award: the open one, else the most recent closed one). Ballot flow: `openBallot`→`renderBallotPick`/`ballotToggle`→`ballotReview` (confirmation: "You are voting for {label} {Primary|Final} Ballot") →`ballotCast` (🗳️ drop animation `.vote-drop`) →`ballotCastResult` (official cast confirmation `.vote-check`). `_ballot` holds the in-progress selection.
- **Client — admin**: `R['voting-admin']` (🗳️ Voting nav) — `loadVotingAdmin`/`renderVotingAdmin`/`votingAdminCard` (state chip, turnout bar, live tally bars), `showNewElectionModal`/`doCreateElection`, `votingSetStatus`/`showReopenModal`/`doReopen`, `showLaunchFinalModal`/`doLaunchFinal` (finalist checkboxes, defaults to top-2 + ties), `doNudge`, `doResetElection`/`doDeleteElection`.
- **Dashboard visibility — `Elections.hidden`** (`'true'`/`''`, added on demand by `ensureElectionColumns_()` from `ensureVotingSheets_()`; also in the schema for fresh installs, no migration). **Orthogonal to open/closed**: hiding pulls a round's chip off every guard dashboard while leaving ballots, receipts, tally and state untouched, so showing it again restores the card exactly as it was. The usual use is clearing the closed cards once voting ends so the banquet award isn't teased for weeks. `electionHidden_(e)` gates `clientVotingCards` (card never rendered), `clientVotingBallot` (non-admins get `forbidden` — a stale card can't be used as a way in) and `clientCastBallot` (`closed`). Admin: `clientSetElectionHidden(id, hidden)` per round + `clientSetAllElectionsHidden(hidden)` for all at once → client `votingSetHidden`/`votingSetAllHidden`, surfaced as a **🙈 Hide card / 👁 Show card** button on each `votingAdminCard` (plus a 🙈 HIDDEN chip) and a **🙈 Hide all cards from dashboards** button in the panel intro. New elections default visible.
- **Test mode**: `test:'true'` election — visible only to an admin session or admin-impersonation, **castable there** (impersonated casting is allowed for test elections only, so the flow can be exercised as different guards); never surfaces to a real guard. Freely reset/deleted; excluded from the one-open-per-award rule.
- **Results are never shown to guards** — admin-only, revealed at the end-of-season banquet. No migration needed — sheets + no config keys auto-create.

## Polls (named ranked-choice group polls — team-photo date, etc.)
- **A separate subsystem from Award Voting** — shares NONE of the voting sheets (`Elections`/`VoteBallots`/`VoteReceipts` are untouched; built this way deliberately so a live vote can't be disturbed). Polls are for group decisions where each guard **ranks their top N options** (default 3) and can flag any option **"🚫 can't do"**. **Not a secret ballot**: responses carry `guard_id`, the admin sees exactly who picked what, and a guard can **change their answer until the poll closes** (one upserted `PollResponses` row per guard).
- **Sheets**: `Polls` + `PollResponses` (auto-created by `ensurePollsSheets_()`, called from every poll endpoint — no migration). Options are stored as JSON `[{id:'o1',label:'…'}]`; `ranking` = ordered array of option ids (best-first, ≤ `rank_count`), `vetoes` = array of "can't do" option ids. A vetoed option is stripped from `ranking` server-side.
- **Scoring** (`pollTally_`): Borda-style — for `rank_count` N a 1st choice scores N points, 2nd N-1, …, Nth 1; unranked = 0. Vetoes counted separately. Results sorted **most points → fewest vetoes → most 1st-place picks**.
- **Lifecycle** (`pollState_`, mirrors `electionState_`): `draft` → `open` (bounded by opens_at/closes_at; **auto-opens/auto-closes** on the window; a future opens_at reports `scheduled`) → `closed`; reopen clears/extends the close time. **Audience** = all active guards (incl. cadets — everyone's in the photo), **snapshotted into `audience_snapshot` when the poll goes live** for a stable turnout denominator. No one-open-at-a-time restriction (unlike voting) — multiple polls can run at once.
- **Results visibility** is a **per-poll admin setting** `results_vis`: `admin` (only admin sees the tally — default), `after` (a guard sees results once they've responded), `live` (always visible to guards). Enforced by `pollResultsVisibleToGuard_`.
- **Server** (`Code.gs`, after the voting section): guard — `clientPollCards` (open polls + most-recent closed, with `hasResponded` + results if visible), `clientPollBallot` (options + the guard's own current ranking/vetoes for editing), `clientSubmitPollResponse` (validates open/audience/pool, upserts under a `LockService` lock). Admin (`requireAdmin`) — `clientPollAdmin` (`pollAdminView_`: turnout + tally + **per-guard `responders` and `pending` lists** — legit since polls aren't anonymous), `clientCreatePoll`, `clientUpdatePoll` (meta always; **options only while zero responses** so the tally can't be corrupted), `clientSetPollStatus` (open/close/reopen), `clientDeletePoll` (drops responses too), `clientPollNudge` (Slack-DMs pending responders, counts only). Helpers: `pollParseJson_`, `pollOptions_`, `pollState_`, `pollAudienceIds_`, `pollTally_`, `pollResultsVisibleToGuard_`, `pollDeleteRowsWhere_`.
- **Client — guard** (`index.html`): `POLLS` global via `loadPolls()` (guard init + GV/impersonation, mirrors `loadVoting`); `pollsCardHtml()` renders a 📋 dashboard card per poll placed **directly below `votingCardsHtml()`** in both dashes. States: respond / "✅ Response saved — tap to change it" / closed (card persists); shows compact results bars (`_pollResultBars`) when visibility allows. Flow: `openPollBallot`→`renderPollBallot` (tap options in preference order → numbered 1️⃣2️⃣3️⃣ badges via `_pollRankToggle`; per-row 🚫 "can't do" via `_pollVetoToggle`)→`submitPollResponse`→`pollSubmitResult` (`.vote-check`, editable-until-close note). Closed polls open read-only via `renderPollClosed`. `_poll` holds the in-progress response.
- **Client — admin**: `R['polls-admin']` (📋 Polls nav) — `loadPollAdmin`/`renderPollAdmin`/`pollAdminCard` (state chip, response bar, ranked-results bars with 🚫veto counts), `showNewPollModal`/`doCreatePoll` (title, question, options textarea one-per-line, rank-top-N, results-visibility select, schedule/close, open-now), `pollSetStatus`/`showPollReopenModal`/`doPollReopen`, `showEditPollModal`/`doUpdatePoll` (options textarea disabled once responses exist), `showPollResponses` (per-guard ranking + can't-dos + pending list), `doPollNudge`, `doDeletePoll`. Helper `_isoToDtLocal` (ISO → datetime-local prefill) added next to `_dtLocalToIso`.
- The `polls` guard panel key exists in `TITLES` only for completeness — polls are surfaced via the dashboard card, not a nav item.

## Last Day of Work (season wind-down)
- Admin flips the ask on; every guard gets a **dashboard banner** asking for the last day they can work, picks it from a **month calendar popup**, and it saves to their roster row. Silent when the ask is off.
- **Storage**: `Guards.last_day` (YMD, blank = open-ended) — added on demand by `ensureGuardColumns_()` (also in the Guards schema for fresh installs, no migration). Config keys: `lastday_active` (`'true'`/`''`), `lastday_message` (optional note shown on the banner), `lastday_season_end` (the date behind the full-season option).
- **"Through the end of the season" option**: the calendar carries a one-tap 🏖️ option that records `lastday_season_end` as the guard's last day — **stored as a plain date, no sentinel value or extra column**, so shading/emails treat it like any other answer. `lastDaySeasonEnd_()` resolves it, defaulting to **Oct 15 of the current season** (rolling to next year once past) when the admin hasn't set one, so the option works before it's configured. "Full season" is derived by comparing `lastDay === seasonEnd` — surfaced as 🏖️ + "Through the end of the season" on the guard card, a selected ✓ state on the option, and a `fullSeason` count in the admin card. ⚠️ Answers are **not** re-pointed if the admin later moves the season end date — a guard's stored date is what they committed to.
- **Downstream effects** — the whole point of collecting it:
  - **Full Schedule** (`R['full-schedule-admin']`, both by-post and by-guard): every day **after** a guard's last day is striped red (`offCls` → CSS `.fsa-off`, an `!important` class rather than an inline background — the weekend/holiday/today/assigned tints are `!important` and would otherwise erase the stripes on those columns), and their name cell carries a `📅 thru <date>` tag (`lastDayTag`). Built from `lastDayBy` off `D.guards`. The **last day itself** gets a pulsing golden glow + a rotated "LAST DAY" stamp (`ldCls`/`ldStamp` → CSS `.fsa-lastday`/`@keyframes ld-glow`/`.ld-stamp`), applied to all four cell paths (by-post and by-guard × assigned and empty).
  - **Weekly schedule emails**: `publishWeek` skips any guard whose last day falls **before the week's Saturday** (`lastDayEndsBeforeWeek_`); the result adds a `doneForSeason` count surfaced in the publish toast. A guard whose last day lands *inside* the week still gets the email.
- **Server** (`Code.gs`, after Cache Hunt): guard — `clientLastDayStatus(token, forGuardId)` (banner state, impersonation-aware like `clientCacheHuntStatus`), `clientSetMyLastDay(token, dateStr)` (blank clears; refuses when the ask is off). Admin (`requireAdmin`) — `clientLastDayAdmin` (toggle + note + season end + every active guard's answer + responded/fullSeason/total), `clientLastDaySave(active, message, seasonEnd)`, `clientSetGuardLastDay(guardId, dateStr)` (corrections / phoned-in answers), `clientLastDayNudge(guardId)` (Slack-DMs guards with no date yet — one id, or `'all'`/omitted for everyone pending; appends the banner note to the DM and **returns counts only**, mirroring `clientPollNudge`). Helpers: `lastDayConfig_`, `normalizeLastDay_`, `guardLastDay_`, `lastDayEndsBeforeWeek_`.
- **Client — guard** (`index.html`): `LASTDAY` global via `loadLastDay()` (guard init + GV/impersonation, mirrors `loadCacheHunt`); `lastDayCardHtml()` renders the banner **at the very top of both dashes**, above `announcementsCardHtml()` (so the voting-below-announcements ordering is untouched). States: not set (coral CTA) / set (green ✓ with the date, tap to change). Flow: `openLastDayModal`→`_renderLastDayCal` (month grid, ‹ › nav floored at the current month, past dates disabled, plus the 🏖️ full-season option) →`_ldPick`/`_ldPickSeason` (jumps the grid to the season-end month)/`_ldNavMonth`→`saveLastDay(ds)` (`''` clears). `_ld` holds the in-progress pick. Blocked during impersonation — only the guard sets their own.
- **Client — admin**: the **📅 Last Day of Work card in the admin Config panel** — `loadLastDayAdmin(keepEdits)`/`renderLastDayAdmin` (active toggle, banner note, response bar, per-guard date inputs), `doSaveLastDayCfg`, `doSetGuardLastDay`/`doClearGuardLastDay`/`_saveGuardLastDay`, `doLastDayNudge(guardId, btn)` (**💬 Nudge all N** button next to the response bar + a per-row **💬 Nudge** that replaces Clear on guards with no date). Needs `slack_bot_token` configured — otherwise the nudge returns `no_slack` and toasts a pointer to Config → 💬 Slack.
  - **Sortable roster**: Guard / Rank / Last day are clickable column headers (`sortLastDay(col)`, state `ldSortCol`+`ldSortDir`, `▲/▼/↕` markers) — same idiom as `sortTimeRecords`. Sorting is client-side off the cached `_ldAdmin` payload (no server round-trip); rank uses the global `RANKS` order, not alphabetical; **blank dates sort first ascending** so un-answered guards surface at the top. Comparison always uses the *saved* value so rows don't jump mid-edit, and `_ldDirty` (+`_ldCaptureEdits`) preserves typed-but-unsaved dates across a re-sort/refresh, flagging them with a coral input border.

## Crew Bingo (photo-night party game)
- A **mode of the existing dashboard Shift Bingo engine**, not a second game. Same 5×5 grid / `WIN_PATTERNS` / marking / win banner; only the cell contents, palette, seed, and localStorage slot swap. `bingoOpen(mode)` — `undefined`/`'shift'` = the everyday easter-egg card of shift happenings (unchanged, still reached by the subtle `#bingo-trigger` "B I N G O" at the bottom of every dash), `'crew'` = the party card where **every cell is a crewmate's name**. Admin projects the crew photos on a screen; guards tap each name as its photo goes up and shout BINGO.
- **Purely client-side play** — nothing is scored, submitted, or stored server-side. The server only answers "is the game on, and which names are in play."
- **Mode plumbing** (`index.html`, the bingo IIFE): `bingoModeCfg(mode)` returns `{mode, items, salt, store, free, subtitle}`; `_bmode`/`_bcfg` hold the active mode. `bingoSeedStr(cfg)` = `salt|hash(items)|date|ident` (`bingoIdent()` = guard email, else a localStorage fingerprint), so **every guard gets a different scramble**, editing the name list re-deals, and a card is stable through the night. `bingoGenBoard(prng, items)` takes the item list. State keys: `bingo_state` (shift) / `bingo_state_crew` / `bingo_state_crew_preview` (admin previews, so they can't clobber a real card). ⚠️ The seed format changed when crew mode landed — existing shift cards regenerate once.
- **Config keys**: `crewbingo_active` (`'true'`/`''`), `crewbingo_title` (event name on the card header), `crewbingo_names` (**one name per line**), `crewbingo_round` (integer folded into the seed — bumping it reshuffles every guard's card mid-game). **24 names minimum** (center is a free space); the server refuses to go live under that. `crewbingo_names` is **filtered out of the generic Config key/value table** — a single-line input would flatten the blob; edit it only in the 🎉 Crew Bingo card.
- **Server** (`Code.gs`, after Cache Hunt): `DEFAULT_CREW_BINGO_NAMES_` (49 names, seeded from the crew photo filenames — the game works before the admin touches anything), `crewBingoNames_()` (parse, trim, dedupe case-insensitively), `crewBingoConfig_()`. Guard — `clientCrewBingo(token)` (returns `{active:false}` unless live **and** ≥24 names). Admin (`requireAdmin`) — `clientCrewBingoAdmin`, `clientCrewBingoSave(active,title,namesText)`, `clientCrewBingoReshuffle`. No sheets, no migration.
- **Client — guard**: `CREWBINGO` global (declared `var` so the bingo IIFE can read it off `window`) via `loadCrewBingo()`; `crewBingoCardHtml()` renders a 🎉 card **above `cacheHuntCardHtml()`** in both dashes, silent when the game is off. `R.dashboard` calls `loadCrewBingo()` on **every** guard dashboard visit (the game gets switched on mid-session), and the loader **re-renders only when the payload actually changed** — an unconditional re-render there would thrash.
- **Client — admin**: the **🎉 Crew Bingo card in the admin Config panel** — `loadCrewBingoAdmin`/`renderCrewBingoAdmin` (live toggle, event name, names textarea, live `cbCount()` readout), `doSaveCrewBingo`, `doPreviewCrewBingo` (deals the admin a card from the **unsaved** textarea contents), `doCrewBingoReshuffle`.
- Crew names are admin-entered, so `bingoRenderGrid` runs cell text through `_esc` before injecting.

## Cache Hunt (GPS treasure hunt easter egg)
- Silent-rollout geocaching game. Admin hides a physical cache holding a **secret code** and records its GPS coords. Guards get **one distance reading per day** (distance-only hint, no direction) from their dashboard to close in, then physically find the cache and **enter the code to win**. ## Shift hours — ONE canonical rule (`shiftTimes`)
- ⚠️ **Never derive a shift's hours off `ShiftTemplates` directly, and never read `custom_start`/`custom_end` directly.** Every view — admin Full Schedule, the guard's own schedule, the single-day crew view, shift cards, the published-schedule email, the iCal feed — resolves hours through one shared helper so what the admin scheduled is exactly what the guard is told.
- The rule:
  - A template **with real hours** (`8HR`, `LS`, `LS8`, `LS10`, `TOURN`, `CADET`…) **IS** the shift's hours. Any `custom_start`/`custom_end` sitting on such a shift is **stale** and ignored (assign paths could copy the guard's S_SPEC availability request onto a plain 8HR, so the admin grid read 8:45–5:15 while the guard's own card read the requested hours).
  - A template with **no hours of its own** (`SPEC` → `start_time` `'TBD'`; `ATH`/`MISC` → `'Custom'`) is defined **only** by the shift's `custom_start`/`custom_end`.
- **Client** (`index.html`, next to `fmtTime`): `tmplHasFixedHours(t)` → `shiftTimes(shift)` `{start,end,custom,tmpl}` → `shiftTimeRange(shift, sep)` (display string) / `shiftPaidHours(shift)` (template hours, or the custom span) / `shiftStartMin`/`shiftEndMin`/`shiftStartKey` (sort keys) / `shiftTimeLabel(s)` (range + `(Nh)`; its legacy `t` argument is ignored).
- **Server** (`Code.gs`, above `toTime24_`): `tmplHasFixedHours_` / `shiftTimes_(shift, tmplByCode)` / `shiftTimeStr_` / `shiftStartMinutes_` — a byte-for-byte mirror of the client rule. **Keep the two in lockstep.**
- Assign/create/edit paths only ever **write** `custom_start`/`custom_end` when the chosen template has no fixed hours (`doAssignShift`, `doForceAssign`, `doMobAssign`, `doCreateShift`, `_commitShiftEdit`); switching a shift back to a fixed-hours template scrubs them. The in/out inputs show/hide on `tmplHasFixedHours`, not on `code==='SPEC'`.
- A shift with **no resolvable hours** renders a coral **⚠ no times** flag on the admin grid + shift manager and reads "hours TBD — see the Supe" in the guard card/email, rather than the old silent blank or literal **"TBD–TBD"**.
- `Shifts.notes` (the admin's free-text label — "Bayshore", "Tournament Day") now propagates to guards too: the day view row, My Schedule cards + detail, and the published email. Grid chips carry it as a `title` tooltip.
- ⚠️ **Known gap, deliberately not changed**: payroll projections still use template `paid_hours` only (`projMins` in `payrollHoursSummary_`, `projectedMins` in `exportTimeRecordsCSV`, `schedMins` in the pay-period change report), so a SPEC/event shift projects **0h** there. Fixing it moves payroll numbers — do it as its own reviewed change.

## Auto-scheduler (`autoAssignWeek`) — phase order
- Daytime phases each sweep the **whole week** before the next runs: beach balance → event requests → flex-off fill (pass 1 ≤5 days, pass 2 the 6th day) → admins.
- ⚠️ **Late shifts are the last phase and must stay there.** By then `assignedByDate` is final for every day, which is what lets an "8HR+LS" guard whose day shift didn't place be left fully off rather than stranded on a lone late.
- Late applicants (guards who requested it in availability) are ordered by **rank, senior first** (`RANK_ORDER_`/`rankIdx_`), then capped at `LATE_CAP_` (6) with an officer guaranteed (`LATE_SENIOR_`).
- **Within a rank the late shifts are balanced across the whole week** — rank is still absolute, but equal-rank applicants are ordered by **fewest late shifts held so far this week** (`lateHeld`, seeded from lates already on the books and incremented as the pass walks Sat→Fri), so when peers vie for the last spot nobody is favored. Tie-breaks after that: **fewest remaining late nights they asked for later in the week** (`lateChancesAfter` — a guard who only requested tonight would otherwise lose their whole week to a peer who requested every night), then `submitted_at`. ⚠️ Don't restore `submitted_at` as the first tie-break — it handed every night to whichever peer filled out availability first.
- Ineligible applicants (already on that night's late, or an "8HR+LS" guard whose day shift didn't place) are **filtered out before the cap slice**, so a skipped pick can't burn one of the 6 spots. Guards cut by the cap are named in the auto-assign warnings.
- ⚠️ **A late pick always books `LS` (5:15–7:15 PM, 2h) — never `LS8`.** `S_LS` is the only late option the availability picker offers (`AV_BASE_OPTIONS`, labelled off the `LS` template), so `LS8` (10:45 AM–7:15 PM, 8h) is a shift no guard can actually request. The scheduler used to "upgrade" a late-only guard — one with no `S_8HR` that day — to a standalone `LS8`, silently replacing the 2-hour evening they signed up for with an 8-hour day starting six hours earlier; it also never invents a daytime shift, so the admin adds the `8HR` by hand if the guard should also work the day. Same rule in `avTemplateCode_('S_LS')` and in the client's `quickAssignLate` (the 🌙 Late Shift Available one-tap assign, which also books on the **Late Shift post** via `latePostId()`, not `D.posts[0]`). `LS8` remains a valid template an admin can assign deliberately — nothing auto-creates it.

## Badges — storage & stickiness
- Badges are **computed live** every load (`computeBadgeMetrics_` + each def's `earned(ctx)` / tiered `metric`), with a persisted `Badges` row written the first time one is earned. **Earned badges are STICKY**: `getBadgeState` (simple) and `tieredBadgeState_` (tiers floored at stored `meta` level) and `computeBadgeLeaderboard_` all treat a stored row as authoritative, so an achievement is **never stripped** if the live metric later dips (broken streak, edited/deleted stat card). Progress bars show full once earned. Rows are never deleted on regression.
  - **Exceptions (stay live, not sticky)**: `manual`/event badges (Treasure Hunter) read only from the sheet; `negative:true` "Hall of Shame" badges (e.g. `sleepyhead`) always reflect live state so a demerit clears when behavior improves.
- **On-time badges (`sharpshooter` 🎯 / `sure_shot` 🏹) — provenance is PER PUNCH, never per record.** `punchProvenance_(r)` → `{inReal, outReal}` decides whether each of a record's two times is the guard's real punch or a hand-set value; `computeBadgeMetrics_` asks it separately for the clock-in and the clock-out. ⚠️ **Never gate these on `Shifts`-style record-level `edited`** — that flag goes true when *either* time is touched, so a guard who nailed 8:45 and then corrected a forgotten clock-out lost credit for the morning punch too. (That bug, plus a pre-2026-07-01 clock-out modal that set `edited='true'` on literally every record, buried both badges for most of the roster — see `ON-TIME-BADGE-AUDIT.md`.) `edited` itself still means "some time on this row changed" and is what the payroll CSV + pay-period change report use; don't repurpose it.
  - **`TimeRecords.clock_in_edited` / `clock_out_edited`** (`'true'`/`'false'`/blank) carry provenance explicitly on new rows — added on demand by `ensureTimeRecordColumns_()`, also in the schema for fresh installs, no migration. Written by `clockIn()` (`in='false'`), `clockOut()` (from the `clockInChanged`/`clockOutChanged` it already computes separately), auto-clock-out (`out='true'`), admin manual entry (both `'true'`), and both edit paths via `onTimePunchProvenanceAfterEdit_()` — which demotes **only the punch that actually moved**.
  - **Legacy rows (blank flags) are inferred, not guessed**: clock-in is real iff `clock_in === created_at` to the ms (`clockIn()` stamps both from one `now`; every override rewrites `clock_in` alone); clock-out is real iff not auto-clocked-out **and** (never `edited`, or `edited_at − clock_out` ∈ `[0, OUT_PIN_GRACE_MS_]` = 150s — the old modal pinned the displayed minute, so an untouched punch lands seconds before the confirm stamp while a typed one lands minutes away or in the future).
  - `auditOnTimeBadges()` retro-credits both badges from full clock history (run once from the editor; idempotent, never downgrades). `auditSharpshooter`/`auditSureShot` are back-compat aliases. `resetOnTimeBadges()` is an escape hatch only — the audit is purely additive.
- **Admin-awarded badges (certifications & accomplishments)** — `manual:true` + `awardable:true` + `secret:true` BADGE_DEFS: `radio_cert`, `cpr_aed`, `first_aid`, `boat_operator`, `jg_instructor` (category `Certifications`), `mvp`, `rescue_season`, `perfect_attendance` (category `Honors`). Never computed — granted/revoked by the admin from the roster's **🎖 Award Badges** button (bulk per-badge: pick a badge → check every guard who should hold it → Save applies the grant/revoke diff). `secret:true` keeps each hidden from a guard's grid until granted (credential style). **Add a cert/honor by dropping one `awardable` entry in BADGE_DEFS** — the picker lists it automatically; no schema/migration. `earned_at` = the admin-chosen grant date; `meta` stores `{by,at}`. Granted badges show in the guard grid, count on the leaderboard (`computeBadgeLeaderboard_` manual branch — **expired certs still count**, but display as expired everywhere), and are shareable like any badge.
  - **Certification expiry** — Certification defs also carry `expires:true`; Honors don't. Stored per-guard in the **`Badges.expires_at`** column (YMD; added on demand by `ensureBadgeColumns_()`, also in the schema for fresh installs — no migration). **Admin-set, per guard** (guards are uninvolved): set in the **per-guard badge editor**, not the bulk screen (bulk can't hold one date per guard). Blank = never expires. Status computed live by `badgeExpiryStatus_` (`CERT_EXPIRING_DAYS_=60`): `valid` / `soon` (≤60 days) / `expired` (past, still held & shown flagged 🔴 — never auto-deleted) / `none` (held, no date). Surfaced to guards read-only via `getBadgeState` (`expires`,`expiresAt`,`expiryStatus`,`expiryDays`) → grid sub-line `_certGridSub` + `showBadgeInfo` expiry line.
  - **Server** (`Code.gs`, after `adminGrantBadge_`): `badgeIsAwardable_`, `clientAwardableBadges` (catalog), `clientBadgeHolders(badgeKey)` (bulk picker pre-check), `clientBulkSetBadge(badgeKey, grantIds, revokeIds, earnedAt)` (bulk grant/revoke diff), `clientGuardBadges(guardId)` (per-guard editor data: held + earnedAt + expiresAt/status per badge), `clientSaveGuardBadges(guardId, items[])` (batch grant/revoke + per-guard expiry), `clientExpiringCerts` (admin report: expired/soon/no-date across active guards + counts). All `requireAdmin`, scoped to `awardable` keys so computed/streak/negative badges can never be touched. Writers: `awardManualBadgeWithMeta_`, `badgeRevokeRow_`. Editor-only `adminGrantBadge_`/`adminRevokeBadge_` remain for computed-badge corrections.
  - **Client** (`index.html`): three roster entry points — **🩺 Cert Status** (topbar → `showCertStatusModal`/`_renderCertStatus`, the expiring/expired report, each row links to the editor), **🎖 Award Badges** (topbar → bulk: `showAwardBadgeModal`/`_renderAwardBadgeModal`/`_awardBadgeChanged`/`_renderAwardRoster`/`saveAwardBadge`, globals `_awardBadges`/`_awardHolders`), and **🎖 Badges per roster row** (`showGuardBadgesModal`/`_renderGuardBadgesModal`/`_gbToggle`/`saveGuardBadges`, globals `_gbGuardId`/`_gbBadges` — the per-guard editor with expiry date fields). Shared status chip `_certStatusChip(status,days)`.
- **`bayshore_late` (🛟 The Real Baywatch)** — worked the Bayshore late shift once. Bayshore has **no post or template code of its own**: it's booked as a **`SPEC` shift with "Bayshore" in `Shifts.notes`** (`isBayshoreShift_`). Matched off the **schedule, not the clock** — guards commonly punch in at 8:45 AM and stay through the Bayshore close on a single time record, so no clock-out window or `LATE_CODES` entry identifies it. `bayshoreDatesFor_` collects a guard's assigned non-cancelled Bayshore dates in `loadBadgeData_` (and per-guard in `computeBadgeLeaderboard_`) → `data.bayshoreDates`; `computeBadgeMetrics_` counts a date only if the guard also has a completed time record that day (`bayshoreLate`).
- **⚠️ Event-shift badges credit off the SCHEDULE, never off the clock** (`tourn_3` 🏆 Craig Hummer, `tourn_5` 🥇 Competitor Supreme, `team_player` 🙌). A time record's `shift_id` is whichever shift the guard **punched in on**, which for an evening event is almost never the event: a day guard punches in on their 8HR shift at 8:45 AM, works the 6 PM tournament, and the `TOURN` assignment appears nowhere in `TimeRecords`; away meets (Belmar, Manasquan) are off-site with no punch at all. The **assignment is the evidence** — a non-cancelled shift carrying the guard's id means they worked it.
  - `BADGE_SHIFT_CODES_` (currently `['TOURN','LS','LS8']`) is the registry. `scheduledEventDates_(allShifts, guardId)` → `{CODE:[ymd]}` feeds `data.eventDates` from `loadBadgeData_` (and per-guard in `computeBadgeLeaderboard_`); `computeBadgeMetrics_` **unions** those with any completed record that *is* linked to a shift of that code (catches a punch on an event later cancelled/reassigned), clamps to **today** (a shift booked for next week can't pre-credit) and to `cutoff`, and exposes `ctx.eventDates` + `tournShifts`/`mcpsTournament2026`. `computeEarnedDates_` includes event dates in its replay candidates so a badge won on an unpunched away day gets the right `earned_at`.
  - **Adding a "worked N shifts of type X" badge = add `X` to `BADGE_SHIFT_CODES_` and read `ctx.eventDates.X`.** Do **not** filter time records by their linked shift's `template_code` — that is the bug that left the whole 2026 roster on 0–2 counted tournaments against 1–5 actually worked, buried both tournament badges for everyone, and forced Team Player to be hand-granted to all 31 guards (see `TOURNAMENT-BADGE-AUDIT.md`).
  - `auditEventShiftBadges()` retro-credits the three badges from schedule history (run once from the editor after deploy; additive, idempotent, back-dates `earned_at`, never downgrades). Needed because a computed badge's `Badges` row is only written when that guard opens their own stats page.
- **`always_be_closing` (🌇 ABC: Always Be Closing) — schedule says WHICH night, clock says they CLOSED.** Same root cause as the tournament badges, from the other direction: a guard who works the day and stays for the close punches **once** at 8:45 AM against their `8HR` shift and out at 7:15 PM, so the record's linked `template_code` reads `8HR` and the `LS` row is never touched. The original gate required that linked code to be an `LS*`, which scored 19 of Abigail Malek's 20 closings as non-closings and left the badge on **zero for the entire roster** — nobody ever reached 10 against 250+ real closes (see `ABC-BADGE-AUDIT.md`).
  - A date counts only when **both** sources agree: a **non-cancelled `LS`/`LS8` assignment** that day (via `ctx.eventDates.LS`/`.LS8`) **AND** a completed, **non-auto-clocked-out** punch clocking out in the closing window `CLOSE_MIN`–`CLOSE_MAX` (6:45 PM–8:00 PM). The assignment alone doesn't prove they stayed; the clock alone can't tell a beach close from a **tournament** ending (seven guards clocked out 7:30 PM on 2026-07-15 off `TOURN` shifts — correctly excluded). Counted by **distinct date**, not by record — two punches in one evening is one close.
  - Auto-clocked-out records are excluded by design (`clock_out` is a duration cap, not a punch) — Abby has 4 more genuine closes that don't count because she forgot to clock out. That's the `sleepyhead` 😴 trade-off, not a bug.
  - `auditClosingBadge()` retro-credits it from schedule history (run once from the editor after deploy; additive, idempotent, back-dates `earned_at`, never downgrades).
- **Stats-streak badges** (`stats_streak_5/10/20/50` — Consistent/Diligent/Meticulous/Spike Fowler) read `statsStreak` = current run of completed shifts with a stat card. **Event shifts don't require a card**: `NO_CARD_CODES` (template_code `TOURN`) are transparent in the streak — a card-less tournament punch neither counts nor breaks the streak (without this, an assigned tournament zeroed the whole streak family). Combined with stickiness, a once-earned streak badge survives even a genuine later break.

## Shift stat cards — multiple per day
- A guard may file **any number of stat cards for one day** (back-to-back Regular + Late Shift on a single time record is the driving case) and may **edit any card until it's archived**. Cards are per-shift, not per-day.
- **Edit vs. new is decided by the client, explicitly — never inferred server-side.** `submitShiftStats` payload carries `stat_id` (edit exactly that card; must belong to the caller) or `new_card:true` (always append). A payload with **neither** falls back to the old date/time-record/shift heuristic — that branch exists only so a **stale cached PWA client** still edits in place instead of piling up duplicates; don't build new flows on it.
- **Day picker**: `openStatsForm` always looks up the day's existing cards first (`clientGetMyStatsForDate` → `getMyShiftStatsForDate`, one date, cheap) and shows `showStatCardPicker` when any exist — list each card (shift · beach · action count) with **Edit**, plus **➕ Add another card**. Only when the day is empty does it open the form directly. Globals `_statPickRec`/`_statPickCards`; handlers `statPickEdit(i)`/`statPickNew()`.
- `showStatsModal(rec, existing)` — **`existing` is passed in or there is none**; it no longer matches a card by date (that guessing is exactly what let a second shift's card overwrite the first). `statId` drives the button label (Save Changes / Submit Stats), the "· editing …" subtitle, and the payload.
- **Draft keys are per-card**: `stats_draft_<date>_<statId|new>` (was per-day), so a recovered draft can't bleed from one of the day's cards into another. The legacy per-day key is cleaned up on a successful save.
- Helpers `_statDateOf(rec)` (normalize to YMD) and `_statRecFromCard(card)` (saved card → the time-record-shaped object the modal wants) are shared by the picker and `editStatCard`.
- Everything downstream already aggregates rather than assuming one card per day — admin totals/`guardTotals`/`missingToday` are set- or sum-based, and the `statsStreak` badge counts *time records that have a card*, so extra cards neither double-count nor break streaks.

## Cadet stat card & badges
- Cadets (rank `Cadet`) get a **different stat card** (same "📋 Shift Statistics" title/nav as guards — not branded "training"). They can't be the primary actor on rescues/first aid or file incident/10-code reports, so those inputs are removed. They **can** log the actions they're permitted: **Preventive Actions**, **Bather Assists**, and the "assisted on another guard's card" checkbox — plus their own training. Beach Location, Shift, Conditions & Weather, and Notes stay.
- Detected client-side by `isCadet()` (index.html, `myGuard().rank === 'cadet'`) and server-side by `isCadetGuard_(guardId)` (Code.gs). One shared `showStatsModal` swaps its middle section (`cadetSection` vs `guardMidSection`); the title is "📋 Shift Statistics" for both.
- **`cadetSection` inputs**: an **Actions** block reusing the guard `numField('preventive')`/`numField('bather')` + the shared `#ss-assisted-other` checkbox (so `submitStatsForm`/prefill pick them up unchanged), then a **Training** block. All cadet training inputs are **numeric count fields** (how many of each completed that day) driven by one single-source list in index.html — `CADET_COUNT_FIELDS` — each `{id, key, label, group}` where `group` is `'water'` (tip-to-tip Swim/Paddle/Run/Kayak, Box Swim, Out-and-Ins) or `'strength'` (Hill Sprints, Pullups, Pushups, Situps, Squats, Burpees, Dune Laps), rendered as two sub-grids. The section HTML, `submitStatsForm` payload, draft prefill, and `myStatsCardRow` summary all iterate this one list, so **adding one cadet input = add a row to `CADET_COUNT_FIELDS` + the matching ShiftStats column (schema + `ensureShiftStatsColumns_` + `submitShiftStats`) + a badge**. All cadet_* columns are numeric. `myStatsCardRow` shows the action count plus a workout summary when a card carries cadet data.
- **ShiftStats columns** (`Code.gs`, all **numeric** — daily counts): `cadet_tip_swim`, `cadet_tip_paddle`, `cadet_run`, `cadet_kayak`, `cadet_box_swim`, `cadet_out_and_ins`, `cadet_hill_sprints`, `cadet_pullups`, `cadet_pushups`, `cadet_situps`, `cadet_squats`, `cadet_burpees`, `cadet_dune_laps` (13 total). Auto-added on demand by `ensureShiftStatsColumns_()` (called from `submitShiftStats`) — no migration needed. Also in the schema for fresh installs and in the `exportShiftStatsCSV` payroll/stats export. (Earlier build stored the six water/distance events as `'true'`/`''` checkboxes — now all counts; any pre-existing `'true'` values read as 0.)
- **Cadet badges** (`BADGE_DEFS`, `category:'Cadet'`, `cadetOnly:true`): rep milestones (tiered) — Pushup Pro 💪 (100/250/500/1k), Pull Your Weight 🧗 pullups (50/150/300/600), Core Crusher 💥 situps (100/250/500/1k), Leg Day 🦵 squats (100/250/500/1k), Burpee Beast 😤 (50/150/300/600), Hill Climber ⛰️ hill-sprint reps (10/30/50/100), Dune Runner 🏜️ dune laps (10/30/50/100); endurance counts (tiered) — Channel Swimmer 🏊 tip swims / Yakker 🛶 tip kayaks / In the Box 📦 box swims (1/10/25/50), Out and Back 🔁 out-and-ins (10/30/50/100); plus Waterman 🌊 (swim+kayak+paddle combo), Pec-Century 💯 (100 pushups in a day), Iron Cadet 🎖️ (every workout type — target `cadetWorkoutTypesTotal`=13). Metrics live in `computeBadgeMetrics_` (`cadetPushups/Pullups/Situps/Squats/Burpees/HillSprints/DuneLaps`, `cadetTipSwim/Kayak/BoxSwim/OutAndIns`, `maxPushupsCard`, `cadetWorkoutsSeen`, `cadetWaterComboSeen`).
- **Badge visibility**: `badgeVisibleFor_(def, isCadet)` — `cadetOnly` badges show only to cadets; `CADET_HIDDEN_BADGES` (primary rescue/first-aid/incident/10-code + on-stand `training` badges like Cross-Trainer/Ryan Matthews/Beach Scholar/Mentor) are hidden from cadets. **Helping Hand (bather_50) and Consolation Prize stay visible** — cadets can log bather assists + assists. Applied in both `getBadgeState` and `computeBadgeLeaderboard_` so grids and the leaderboard stay consistent. Universal badges (hours, streaks, weather, endurance, punctuality, diligence) also apply to cadets.
